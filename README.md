## Идея

«Учебный день под контролем». Студент начинает с ближайшего занятия, видит изменение аудитории, срок проекта и состояние обращения. Главная отвечает на вопрос «Что сейчас важно?», остальные разделы раскрывают детали. Это продуктовая гипотеза: интервью и опросы студентов в этой сессии не проводились.

## Локальная сборка Worker (ранняя конфигурация)

Нужны Node.js 24 LTS (проверено 24.19.0), npm, доступ к npm registry. Windows PowerShell поддерживается. Git и tar нужны для публикации через Sites.

Откройте терминал в папке исходников `digital-dean`:

```sh
npm ci
npm run db:setup
npm run dev -- --port 5173
```

Откройте [локальное приложение](http://127.0.0.1:5173/login). Остановка — Ctrl+C в терминале сервера. Повторный запуск не удаляет базу. Не удаляйте `.wrangler/state` между запусками, если хотите сохранить заявки и прочтения.

```sh
npm test
npm run typecheck
npm run build
npm start -- --port 5173
```

`npm start` запускает собранный Worker локально; предварительно нужны build и db:setup. Dev и start используют одну `.wrangler/state`. Не запускайте два сервера на одном порту.

Отдельные команды: `npm run db:generate` генерирует миграции Drizzle, `npm run db:migrate` применяет только неприменённые локальные миграции, `npm run db:seed` обновляет хеши в стартовой базе из `ORBIT_ALINA_PASSWORD` и `ORBIT_MARK_PASSWORD`. Затем `npm run db:setup` применяет набор в локальную БД. Повторный seed использует INSERT OR IGNORE, не создаёт дубли и не сбрасывает созданные заявки или прочтения. Уже существующие пароли не заменяются новым seed.

Переменные окружения для демоверсии не обязательны. `.env.example` содержит только необязательные флаги Wrangler. Настоящие секреты в `.env`/`.dev.vars` не коммитятся. `TEST_BASE_URL` позволяет направить `node scripts/http-smoke.mjs` на локальный HTTP-сервер. Задайте тестовые пароли через `ORBIT_ALINA_PASSWORD` и `ORBIT_MARK_PASSWORD`. Проверка создаёт вымышленную заявку и проверяет её сохранение.

## Разделы

- Главная: приоритеты дня, текущая или следующая пара, изменение аудитории, срок, обращение и непрочитанные уведомления.
- Расписание: день/неделя, выбор даты и соседних периодов, карточки занятий, вымышленные перенос и отмена. Вне подготовленной недели показано честное пустое состояние.
- Успеваемость: шесть дисциплин на студента, оценки/зачёт, даты, статусы и ближайшее учебное событие. Сводные числа вычисляются из записей.
- Заявки: четыре типа, проверка полей, подтверждение сохранения в прототипе, детали и история статусов. Новые заявки остаются «Принята»; сотрудник или автоматическая обработка не имитируются.
- Уведомления: все/непрочитанные, одно/все прочитаны, счётчик, переход к связанному занятию, оценкам или заявке.
- Профиль: вошедший студент, институт, направление, группа и выход.

## Архитектура и хранение

TypeScript + React 19 + Vinext/Vite: единый интерфейс и серверные маршруты. Выбран готовый поддерживаемый Sites starter. Cloudflare D1 хранит записи; Drizzle описывает схему и генерирует SQL. Для SQL запросов используется маленький общий серверный модуль `lib/api.mjs`, чтобы тестировать те же правила доступа без браузера.

Локально Wrangler эмулирует D1 постоянным SQLite файлом в `.wrangler/state/v3/d1`. На Sites используется отдельная постоянная облачная D1 с той же миграцией; локальные заявки туда автоматически не переносятся. Данные не хранятся в localStorage. Node-вариант использует тот же SQL-адаптер с синхронным атомарным batch; Cloudflare-вариант по-прежнему работает с D1. Это два отдельных постоянных хранилища, а не localStorage.

Сущности: students, credentials, sessions, disciplines, lessons, results, requests, request_history, notifications, notification_reads, events, plan_marks; login_limits ограничивает частоту входа. Связи — по ID, внешние ключи и индексы владельцев заданы в схеме. Создание заявки и первой записи истории — атомарный batch; UNIQUE(student_id,idempotency_key) исключает дубли повторной отправки.

Вход проверяется сервером. Пароль хранится как PBKDF2-SHA256, 100000 итераций, случайная соль 16 байт. Сервер генерирует случайную сессию 32 байта, в БД хранит SHA256 токена и срок 12 часов. Клиент получает только HttpOnly/SameSite=Lax cookie; HTTPS добавляет Secure. Сессия обновляется при входе и удаляется при выходе. Ответы закрытых страниц и API не кешируются.

Каждый закрытый API проверяет сессию и выбирает записи только её владельца. Переданный клиентом studentId не используется. Чужой ID и отсутствующий ID возвращают одинаковый 404. POST требует совпадения Origin; внешние cross-site запросы отклоняются. Сервер повторно валидирует форму, ограничивает длину и возвращает ошибки полей. Поля с паролями, хешами и токенами не попадают в JSON ответов или логи.

В интерфейсе намеренно зафиксированы демонстрационные часы: 2026-11-09 10:15 Europe/Moscow и неделя 2026-11-09–2026-11-15. Это объяснено пользователю, данные не выдаются за живое расписание. Новые заявки и прочтения сохраняют фактическое время сервера ISO 8601, интерфейс отображает Europe/Moscow.

## Публикация

Текущий проект настроен под Sites: `.openai/hosting.json` содержит настоящий project_id, binding D1 называется DB. Повторно создавать Site для этого проекта нельзя.

1. Установить зависимости, выполнить test/typecheck и build.
2. При новой схеме выполнить db:generate, проверить SQL и зафиксировать миграцию. Уже применённые миграции не менять.
3. Через Sites получить действующие права записи исходников этого же проекта.
4. Helper `site-workflow.mjs` плагина Sites синхронизирует Git и собирает архив именно из отправленного commit. Передавать credential через stdin, не записывать токен в файл или командную строку.
5. Сохранить версию и развернуть её нативным инструментом Sites с project_id/commit_sha/archive. Sites применит миграции и создаст D1. На первом запросе seed добавит отсутствующие вымышленные записи; повторное выполнение сохраняет существующие.
6. Дождаться terminal status succeeded. Проверить оба аккаунта, заявку, перезагрузку, выход и чужой ID уже по размещённому адресу.
7. Этот Sites уже открыт всем по ссылке по явному указанию пользователя. Вход через ChatGPT не требуется; вход под тестовым студентом остаётся обязательным. При дальнейших публикациях сохраняйте выбранный публичный доступ. Проверьте конкурсную ссылку в браузере жюри.

Для самостоятельного Cloudflare Workers размещения нужны аккаунт Cloudflare, D1, HTTPS домен и binding DB. `dist/server/wrangler.json` — generated build configuration; подставьте ID вашей D1 вне исходников, примените `drizzle/*.sql`, затем разверните Worker через Wrangler. Sites не требует отдельного внешнего API вуза, почтового сервиса или платных ИИ-ключей.

Доступность текущей ссылки из России без VPN не выполнена на сети пользователя по его проверке 2026-11-10. По [официальной справке Cloudflare](https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/), проверенной 2026-11-10, некоторые российские провайдеры ограничивают трафик Cloudflare. Это риск выбранной площадки, а не доказательство доступности конкретной ссылки. Команда должна проверить домашнюю и мобильную сети без VPN; если ссылка недоступна, выбрать площадку после отдельной проверки и перенести Worker/D1 либо адаптировать приложение для другого серверного хостинга. Работа ссылки до 2026-11-28 не гарантируется этой сессией.

## Ограничения

Это демонстрационная система с общими публичными тестовыми аккаунтами. Любой допущенный посетитель, знающий демопароль, может видеть тестовые обращения этого аккаунта. Расписание идёт живым потоком из РЭУ, а вход и баллы работают на демонстрационных данных: архитектура подключения готова, доступа от университета ещё нет (см. «Подключение к системам РЭУ»). Нет регистрации, восстановления пароля, сотрудника, реального документа, отправки в вуз и вложений. Статусы в seed — вымышленные примеры, новые заявки автоматически не обрабатываются. Парольный алгоритм и rate limiting выбраны для ограниченного прототипа; для настоящего сервиса нужны отдельное проектирование безопасности, эксплуатационный мониторинг, резервное копирование, нагрузочная проверка и независимое ревью. Не использовать для настоящих персональных данных.

## Подключение к системам РЭУ, 2026-11-15

Портал разделён на три источника данных, и каждый из них честно подписан в интерфейсе (карточка «Откуда данные» в профиле).

Расписание уже живое и не требует настроек. «Орбита» запрашивает неделю у публичного экспорта `rasp.rea.ru` для любой из 1074 групп справочника: страница `/timetable` открыта без входа, в кабинете та же живая неделя подставляется вместо сохранённого снимка. Номер группы проверяется по справочнику, ответ кешируется 15 минут, на один адрес — 30 открытий недели в минуту.

Вход и баллы устроены как адаптеры с двумя режимами. По умолчанию работают демонстрационные записи «Орбиты» и рейтинг, рассчитанный по Положению РЭУ. Когда университет выдаст доступ, режимы переключаются переменными окружения, и код приложения не меняется:

- `ORBIT_IDENTITY=oidc` — единый вход РЭУ: authorization code + PKCE S256, проверка подписи `id_token` по JWKS, подписанная cookie перелёта на 10 минут. Пароль студента портал не видит.
- `ORBIT_GRADES=university` — ведомость университета: один служебный GET с токеном, строгая проверка формата и шкалы. При отклонении формата показывается ошибка, а не демонстрационные баллы.

Полный контракт для ИТ-службы вуза — [docs/ПОДКЛЮЧЕНИЕ-РЭУ.md](docs/ПОДКЛЮЧЕНИЕ-РЭУ.md), переменные — в `.env.example`. Подключение покрыто `tests/sources.test.mjs`: 4 проверки из 17, сеть в них подменяется заглушками.
