# Подключение «Орбиты» к системам РЭУ

Документ для ИТ-службы университета. Описывает, что «Орбите» нужно от РЭУ,
чтобы портал перестал быть демонстрацией, и что для этого уже готово в коде.
Изменений в приложении подключение не требует: всё включается переменными
окружения (`.env.example`).

Дата документа: 15 ноября 2026 года.

## Три источника данных

| Источник | Сейчас | После подключения | Переключатель |
|---|---|---|---|
| Расписание | Живые данные РЭУ | Без изменений | — |
| Вход студента | Демонстрационные записи «Орбиты» | Единый вход РЭУ (OpenID Connect) | `ORBIT_IDENTITY=oidc` |
| Баллы | Демонстрационный рейтинг по Положению РЭУ | Ведомость университета | `ORBIT_GRADES=university` |

Режим каждого источника виден в интерфейсе: в профиле студента есть карточка
«Откуда данные», а открытая страница расписания и экран входа называют источник
прямо на месте. Портал нигде не выдаёт демонстрационные данные за университетские.

## 1. Расписание — работает уже сейчас

«Орбита» читает публичный экспорт расписания `https://rasp.rea.ru` (тот же
календарь, который университет отдаёт студентам по кнопке экспорта).

- Номер группы проверяется по справочнику `public/reu-groups.json` (1074 группы,
  18 подразделений) — к университету уходит только существующий код группы.
- Запрашивается одна неделя: `Schedule/ExportCalendar` → `Schedule/GetFile`.
- Ответ кешируется на 15 минут, одновременно не более 4 запросов, таймаут 12 с,
  ограничение по IP — 30 открытий недели в минуту.
- Авторизация не нужна: пароль студента в этом сценарии не используется.

Открытый адрес портала: `/timetable` (страница) и `/api/public/schedule?group=…&date=…&view=day|week`.

Если университет предпочтёт служебный API вместо публичного экспорта, нужен
адрес и формат; код источника изолирован в `lib/rea-live.mjs`.

## 2. Единый вход (OpenID Connect) — ждёт регистрации клиента

«Орбита» реализует authorization code flow с PKCE S256 и проверкой подписи
`id_token` по JWKS (RS256 или ES256). Пароль студента портал не видит и не хранит.

Что нужно от РЭУ:

| Параметр | Значение |
|---|---|
| Тип клиента | confidential, authorization code + PKCE |
| Redirect URI | `https://<адрес портала>/api/auth/oidc/callback` |
| Post-logout URI | `https://<адрес портала>/login` |
| Scopes | `openid profile` (достаточно) |
| Выдать | `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` |

Издатель должен отдавать `GET {issuer}/.well-known/openid-configuration` с полями
`issuer`, `authorization_endpoint`, `token_endpoint`, `jwks_uri`.

Утверждения (claims) в `id_token`:

| Claim | Назначение | Обязателен |
|---|---|---|
| `sub` | Устойчивый идентификатор студента | да |
| `preferred_username` | Логин для подписи профиля | нет |
| `family_name`, `given_name`, `middle_name` | ФИО | желательно |
| `group` | Номер учебной группы, как в расписании РЭУ | да, иначе не будет расписания |
| `institute`, `program` | Подразделение и образовательная программа | желательно |
| `course`, `semester` | Курс и семестр (целые числа) | желательно |

Если имена утверждений в РЭУ другие, их не нужно менять: соответствие задаётся
переменными `OIDC_GROUP_CLAIM`, `OIDC_INSTITUTE_CLAIM`, `OIDC_PROGRAM_CLAIM`,
`OIDC_COURSE_CLAIM`, `OIDC_SEMESTER_CLAIM`, `OIDC_LOGIN_CLAIM`.

Как «Орбита» проверяет удостоверение: совпадение `iss`, наличие `client_id`
в `aud`, срок `exp`, разумность `iat`, совпадение `nonce` с тем, что отправлен
в запросе, и подпись по ключу из `jwks_uri`. Состояние перелёта (`state`,
`nonce`, PKCE-проверка) живёт 10 минут в cookie, подписанной HMAC-SHA-256
на ключе `ORBIT_AUTH_SECRET`; попытки входа ограничены 20 в минуту на адрес.

Профиль студента записывается в базу портала с идентификатором
`sso-<первые 10 байт SHA-256 от issuer + sub>`: повторный вход находит ту же
запись и обновляет её, второй учётной записи не появляется.

## 3. Ведомость (баллы) — ждёт служебного доступа

«Орбита» ожидает один служебный метод, который по логину студента возвращает его
результаты за семестр.

```
GET {UNIVERSITY_GRADES_URL}?login=<логин студента>
Authorization: Bearer {UNIVERSITY_GRADES_TOKEN}
Accept: application/json
```

Ответ:

```json
{
  "grades": [
    {
      "id": "reu-2026-1-econ",
      "subject": "Экономическая теория",
      "credits": 4,
      "result": "5",
      "status": "Зачтено",
      "updatedAt": "2026-11-10",
      "nextDate": "2026-12-18",
      "nextKind": "Экзамен",
      "rating": {
        "participation": 18,
        "control": 19,
        "creative": 16,
        "assessment": 38
      }
    }
  ]
}
```

Правила:

- `subject` обязателен; `rating` можно не присылать, пока результат не опубликован —
  портал покажет «Ожидает результата».
- Шкала из Положения РЭУ о рейтинговой системе: `participation`, `control`,
  `creative` — до 20 баллов, `assessment` — до 40, сумму считает портал.
- `nextDate` — в формате `ГГГГ-ММ-ДД`. Не более 200 дисциплин в ответе.
- Таймаут запроса 10 секунд. Отклонение от формата или балл вне шкалы —
  это ошибка: портал покажет «Ведомость РЭУ недоступна», а не подставит
  демонстрационные баллы.
- Служебный ключ остаётся на сервере и в браузер не передаётся (проверено тестом).

Если удобнее отдавать данные по `sub` из единого входа, а не по логину —
скажите, параметр запроса изменится одной строкой в `lib/sources.mjs`.

## Что проверено тестами

`npm test` (17 проверок, из них 4 — про это подключение, `tests/sources.test.mjs`):

- режимы источников и явные сообщения о недостающих настройках;
- открытое расписание: живая неделя, отказ для группы вне справочника, лимит запросов;
- единый вход: перелёт с PKCE, отказ при подделке подписи, чужом `state` и чужом
  `aud`, повторный вход того же студента не создаёт вторую запись;
- ведомость: сопоставление полей, строгая проверка шкалы, служебный ключ
  не утекает в ответ браузеру.

## Защита персональных данных

- Портал не просит и не хранит пароль студента ни в одном режиме.
- Сессия — HttpOnly-cookie на 12 часов, в базе только SHA-256 от токена.
- Расписание запрашивается без авторизации, по публичному экспорту.
- Демонстрационные профили не содержат настоящих персональных данных.
- Обращения и личные заметки остаются в базе портала и в системы РЭУ не уходят.

## Контрольный список подключения

1. Зарегистрировать клиента единого входа, выдать issuer, client_id, client_secret.
2. Проверить, что в `id_token` есть `sub` и номер группы.
3. Задать `ORBIT_IDENTITY=oidc` и ключи окружения, перезапустить портал.
4. Открыть служебный доступ к ведомости, выдать адрес и токен.
5. Задать `ORBIT_GRADES=university`.
6. Проверить вход студентом и сверить его баллы с ЛКС.
